## 1. Найденные дефекты безопасности

### 🔴 S2 · SEC-00. Живые ключи DaData в исходниках и в отслеживаемом файле данных

**Место:** `server.ts:3560-3561` (`DEFAULT_DADATA_API_KEY`, `DEFAULT_DADATA_SECRET_KEY`), повторно `server.ts:3647-3648` (`DEFAULT_WORKING_TOKEN`, `DEFAULT_WORKING_SECRET`), `data/crm_settings.json` (те же значения).
**Доказательство:** 40-символьные hex-строки формата DaData; используются как фолбэк при пустом env (`if (!candidateKey) candidateKey = DEFAULT_DADATA_API_KEY`) и как «верифицированный рабочий токен» для повторного запроса при `401/403`. Рядом лежал `DISABLED_SUGGESTION_KEYS` с тем же секретом — признак, что ключ уже блокировали.
**Важно:** резолвер читал `data/crm_settings.json` **раньше** env, поэтому удаление литералов из `server.ts` без правки файла не меняло бы ничего — скомпрометированный ключ продолжал бы работать.
**Влияние:** публичный репозиторий = источник действующих реквизитов: расход платной квоты, журнал запросов компании (ИНН/ОГРН заказчиков) в чужом аккаунте, при секрет-ключе — управление настройками аккаунта DaData.
**Исправлено:** литералы удалены, `data/crm_settings.json` обнулён, изъят из индекса и добавлен в `.gitignore`; при отсутствии ключа `/api/dadata/*` отвечает `503` с текстом инструкции. **Ротацию ключей выполняет владелец аккаунта** — в истории коммитов (`cfe8178`) они остаются.

### 🔴 S2 · SEC-01. Анонимное уничтожение таблицы пользователей

**Место:** `POST /api/users/sync` (`server.ts:2977-2998` до правки).
**Доказательство:** `if (resetToDefaults === true) { await db.delete(schema.users); await seedInitialUsersIfEmpty(DEFAULT_SYSTEM_USERS); }` — без аутентификации, без подтверждения; ответ содержит весь список пользователей с паролями.
**Влияние:** один `curl` стирает всех B2B-заказчиков и возвращает учётные данные демо-аккаунтов (`admin123`).
**Исправлено:** роут под `requireAdmin`, сброс дополнительно требует `ALLOW_USER_SYNC_RESET=true`; ответ фильтруется `stripSecrets`.

### 🔴 S2 · SEC-02. Пароли всех пользователей в HTTP-ответе

**Место:** `GET /api/users` (`server.ts:2823`) → `getAllDbUsers()`; `src/db/users.ts:326, 371, 601, 629` — `password: r.password || '123456'`.
**Влияние:** открытым текстом выдаются пароли 9+ учётных записей, включая `adm-01` (генеральный директор); пароли не хешируются нигде в проекте.
**Исправлено:** все ответы `/api/users*` проходят `stripSecrets` (граница наружу). Хранилище (plain-text в `users`) — отдельная задача с миграцией формата; в `data/users.json` (disk fallback) пароли по-прежнему лежат.

### 🟠 S2/S3 · SEC-03. Саморегистрация superadmin и флуд уведомлений

**Место:** `POST /api/users` (`server.ts:2848-2872`).
**Доказательство:** из тела принимались `role`, `permissions` и `id`; `createDbUser({ id, role: role || 'client', permissions, password, ... })`, затем `dispatchManagerNotification(...)` на каждую запись.
**Влияние:** эскалация привилегий до `superadmin`, перезапись существующей учётки чужим `id`, рассылка писем/попапов менеджерам как усилитель спама (лимитер обходился поддельным `X-Forwarded-For`).
**Исправлено:** `sanitizeUserInput` — роль `client`, `permissions` базовые, `id` генерирует сервер, `password` из тела игнорируется; задавать роль может только держатель реально принятого `ADMIN_API_TOKEN`. Отдельно исправлено следствие первой версии правки: «dev-режим» не должен означать «админ» (см. п. 3, NOTE-2).

### 🔴 S2 · SEC-04. Пароли приложения в коде + аддитивная маска

**Место:** `src/server/emailModule.ts:157, 176, 195, 214, 233, 252, 268` — `pass: 'ds_app_nekrasov_2026'` и ещё пять; `getSmtpSettings()` (`:334-341`) добавлял `passMasked`, **не удаляя** `pass`.
**Влияние:** `GET /api/email/settings` (без прав) отдавал пароль SMTP и пароли приложения шести сотрудников; значения доступны и из клонированного репозитория.
**Исправлено:** пароли только из env (`DS_SMTP_APP_PASSWORDS` — JSON-карта по `managerId`, либо `DS_SMTP_APP_PASSWORD_ADM_01`… ; глобальный — `SMTP_PASS`), геттер возвращает `pass: ''` + `passConfigured`, ответы роутов — через белый список `SMTP_PUBLIC_FIELDS`.

**Доказательство:** без аутентификации принимались `host`, `port`, `secure`, `user`, `pass`, `fromEmail`, `replyTo`; обход «демо-кредел» — `isDemoCredential` (`emailModule.ts:625`) считал демо только пароль с префиксом `ds_app_`.
**Влияние:** перенаправление всей корреспонденции на сервер атакующего (и отправка от имени `info@ds-enginering.ru`), в т. ч. писем с условиями договоров.

### 🟠 S2 · SEC-07. ПДн заявителей в живом журнале и в stdout

**Место:** `GET /api/crm/realtime-logs` (`server.ts:2602`), очистка `POST /api/crm/realtime-logs/clear` (`:2615`); источники — `server.ts:1062-1067, 1226-1230, 2109`; `src/server/logger.ts:15-39` (буфер 200 записей + `console.log(JSON.stringify(entry.details))`).

### 🟠 S3 · SEC-09. «Строгая валидация», пропускающая любые поля

**Место:** `src/server/schemas/jsonSchemas.ts` — `additionalProperties: true` в 12 схемах из 13; `src/server/schemas/validator.ts:8-12` — Ajv без `removeAdditional`; потребители вида `{ ...current, ...payload }` (`src/server/priceListsModule.ts:389-390`).
**Влияние:** mass assignment: в сохранённую позицию прайса и в прочие сущности попадают любые поля запроса.

Четыре поля в схемы добавлены (контракт совпадает), причина отказа от опции зафиксирована комментарием в `validator.ts`; включать строгость нужно отдельным пакетом с контрактовыми тестами четырёх роутов.

**Исправлено:** `requireAdmin`, 512 КБ на значение, 200 ключей с вытеснением старых (проверено: 700 КБ → `413`, 1 КБ → `200`). Path traversal здесь не было: ключ уходит параметризованным запросом в Drizzle.

### 🟡 S3 · SEC-12. Доверие `X-Forwarded-For` при лимитере и отсутствие `trust proxy`

**Место:** `server.ts:309` — `const ip = (req.headers['x-forwarded-for'] as string) || req.socket.remoteAddress`; `app.set('trust proxy', …)` в файле нет.

## 3. Что найдено по ходу исправлений (регрессии собственных правок)

- **NOTE-1.** `data/crm_settings.json` содержал те же ключи, что и код, и читался раньше env → без изъятия файла из git правка SEC-00 была бы косметической.
- **NOTE-2.** Первая версия SEC-03 считала caller'а администратором, если `evaluateAdminAccess(...).ok`; в dev без токена `ok === true`, поэтому форма саморегистрации получала право задавать роль ровно там, где доступ никто не проверяет. Право даёт только `reason === 'token'`. Поймано живым смоуком, не ревью.
- **NOTE-3.** Включение `removeAdditional: 'all'` (первоначальная рекомендация SEC-09) молча ломало бы 4 публичных роута — см. формулировку SEC-09 выше.
- **NOTE-4.** Маскирование только `details` не закрывало SEC-07: `summary` строился шаблоном с ФИО и телефоном целиком. Добавлены `redactText` (телефон/почта в свободных строках) и маскирование у источников; отдельно зафиксировано тестами, что даты и артикулы не портятся.
- **NOTE-5.** `logger.ts` писал `details` в `console.log` → ПДн дублировались в stdout контейнера (вне контроля доступа). Теперь и там маска.

## 5. Порядок дальнейшей работы

1. **SEC-00 ротация**: выпустить новые ключи DaData в кабинете dadata.ru; старые останутся в истории `cfe8178`. 5. **LOG-04**: монтировать `/uploads`, читать ассеты из каталога записи (или писать в `dist/assets` на лету), добавить `fileFilter` по расширениям.
6. **SEC-09 (строгость Ajv)**: дополнить схемы свободными вложенностями через `patternProperties`, написать контрактовые тесты четырёх роутов, затем включать `removeAdditional`.
