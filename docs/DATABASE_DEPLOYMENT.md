# РУКОВОДСТВО ПО РАЗВЕРТЫВАНИЮ БАЗЫ ДАННЫХ
*(Для системных администраторов и инженеров DevOps «ДС-Инжиниринг»)*

Корпоративный портал компании «ДС-Инжиниринг» использует реляционную систему управления базами данных **PostgreSQL 17** (образ `postgres:17-alpine`) в связке с TypeScript ORM **Drizzle ORM** (`drizzle-orm/node-postgres`) и пулом соединений `pg`. При недоступности БД портал автоматически активирует гибридный отказоустойчивый режим (In-Memory + автосохранение на диск в `data/`).

## 1. Системные требования
- **ОС:** Ubuntu 22.04/24.04 LTS (или любая Linux/Unix ОС с поддержкой Docker)
- **СУБД:** **PostgreSQL 17** (официальный образ `postgres:17-alpine`)
- **Установленное ПО:** Docker Engine 24+, Docker Compose v2+
- **Порты:** 5432 (PostgreSQL), 3000 (Node.js/Express Web Application)

## 2. Развертывание PostgreSQL 17 (через Docker Compose)

В корневой директории проекта расположен файл `docker-compose.yml`. Для запуска базы данных PostgreSQL 17 выполните команду:

```bash
docker-compose up -d postgres
```

Команда загрузит образ `postgres:17-alpine`, запустит контейнер `ds_engineering_db` и подключит постоянный том `pgdata` для сохранения информации.


## 4. Инициализация и обновление структуры таблиц (Миграции)

После запуска базы данных необходимо создать таблицы. В проекте используется Drizzle ORM для управления структурой базы данных. 

Выполните команду для автоматической генерации и отправки схемы (`users`, `tickets`, `rfq_submissions`) в базу:

```bash
# Применяем схему к базе данных напрямую
npm run db:push
```

## 5. Графический интерфейс управления базой данных (Drizzle Studio)

Чтобы не устанавливать сторонние программы типа pgAdmin или DBeaver, в проект встроена локальная панель администрирования — **Drizzle Studio**.

Для запуска админ-панели выполните команду:
```bash
npm run db:studio
```
В терминале появится ссылка (обычно `https://local.drizzle.studio`), перейдя по которой вы получите полный доступ ко всем таблицам, сможете просматривать заявки, тикеты и пользователей напрямую в браузере.

## 6. Резервное копирование (Backups)

Поскольку база данных работает в Docker, все файлы хранятся в томе `pgdata`. 
Для снятия полного SQL-дампа базы (без остановки сервиса) используйте команду:

```bash
docker exec -t ds_engineering_db pg_dumpall -c -U ds_admin > ds_engineering_dump_$(date +%Y-%m-%d).sql
```
Рекомендуется добавить данную команду в `cron` для ежедневного резервного копирования.

## 7. Структура таблиц и гибридная персистентность (Drizzle ORM)

В реляционную схему включены следующие основные таблицы:
- `users` — учетные записи сотрудников и клиентов компании с ролевой моделью RBAC.
- `tickets` — техническая поддержка B2B и заявки клиентов.
- `rfq_submissions` — запросы коммерческих предложений и расчеты калькулятора.
- `service_requests` — выездные заявки на 3D-контроль, калибровку и сервис КИМ.
- `crm_fleet_devices` — реестр средств измерений и физического парка приборов (КИМ типа «рука», сканеры, лазерные трекеры) со сроками поверки ФГИС «АРШИН».
- `crm_certificates` — реестр свидетельств об обучении, инструктажах по ТБ и аттестации метрологов (REST API `/api/crm/certificates`).
- `cms_store` / `text_constants` / `company_positions` — персистентное хранилище конфигураций CMS, специализированная SQL-таблица текстовых констант сайта (`text_constants` с эндпоинтом `/api/text-constants`), глобальные настройки (`site_text_constants`) и общекорпоративный справочник должностей сотрудников компании.

При автономной работе или временной недоступности PostgreSQL сервер автоматически сохраняет состояние в JSON-файлы с дисковой персистентностью в папке `data/` (`data/crm_fleet_devices.json`, `data/certificates.json`, `data/serviceRequests.json`, `data/botTopics.json`, `data/company_positions.json`, `data/site_texts.json`).

## 8. Таблица `text_constants`, REST API и обработка ошибок подключения к БД

Таблица `text_constants` предназначена для строго типизированного хранения ключевых текстовых полей сайта (телефон, адрес, слоганы, заголовки услуг) в реляционном виде:
* **Колонки:** `id` (serial primary key), `key` (varchar 128 unique), `category` (varchar 64), `value` (text), `description` (varchar 255), `updated_at` (timestamp with timezone).
* **Основной эндпоинт извлечения:**
  * `GET /api/text-constants` (алиасы: `/api/text_constants`, `/api/text-constants/all`)
  * Параметры фильтрации: `?category=contacts`, `?key=contacts.phoneMain`.
  * Формат ответа: `application/json; charset=utf-8` со структурой `{ success: true, source: "database_table", table: "text_constants", count: N, total: N, constants: [...], records: [...], dictionary: {...} }`.
* **Обработка ошибок подключения к базе данных:**
  * При сбое подключения к PostgreSQL (ECONNREFUSED, ETIMEDOUT, сбой авторизации или обрыв пула) сервер возвращает HTTP 500 / 503 со структурированным телом:
    ```json
    {
      "success": false,
      "error": "Ошибка подключения к базе данных",
      "message": "Не удалось извлечь текстовые константы из таблицы \"text_constants\" из-за ошибки подключения к PostgreSQL",
      "code": "DB_CONNECTION_ERROR",
      "table": "text_constants",
      "timestamp": "2026-09-11T..."
    }
    ```
  * При передаче параметра `?fallback=true` или заголовка `X-Allow-Fallback: true` сервер возвращает данные из локального хранилища с пометкой `source: "fallback_after_db_error"`, обеспечивая непрерывную работу сайта.
  * При передаче `?strict=true` / `?require_db=true` эндпоинт производит строгую валидацию связи с СУБД.
  * Диагностический эндпоинт: `GET /api/text-constants/health` возвращает статус подключения к таблице `text_constants`.

### 8.1. Клиентская подгрузка и авто-seeding констант (`AppProvider` & `siteTextsModule`)
- **Авто-seeding при первом запуске:** при обращении к `GET /api/text-constants` бэкенд проверяет наличие записей в таблице `text_constants`. Если таблица пуста, сервер автоматически наполняет ее всеми стандартными константами (`DEFAULT_SITE_TEXTS`) с присвоением категорий (`home`, `about`, `contacts`, `services`, `catalogs`, `footer`).
- **Сквозная инициализация во фронтенде:** клиентский провайдер `<AppProvider>` (`src/context/AppContext.tsx`) при монтировании вызывает `fetchGlobalTextConstants()`. Полученный словарь `dictionary` кэшируется в плоском виде `textConstants: Record<string, string>`, а также реконструируется в древовидный объект `siteTexts: SiteTextsData` с помощью функции `reconstructSiteTextsFromDictionary`.
- **Быстрый O(1) доступ:** хелпер `getText(key, fallback)` гарантирует мгновенную отдачу значения константы без повторных обращений к сети и каскадный fallback при сбоях.

## 9. Хранилище данных и агрегаты CRM-дашборда (CrmDashboard)

Инженерный дашборд CRM агрегирует данные из реляционных таблиц и персистентного хранилища:
- **`deals` (Сделки и воронка):** расчет `Total Pipeline Value`, средневзвешенного объема и этапов конверсии (`lead`, `audit`, `tender`, `contract`, `closed_won`);
- **`service_requests` / `serviceRequests.json`:** фиксация входящих запросов (`Recent Requests`), времени поступления, канала (Сайт, МАКС-бот, Telegram) и соблюдения регламента SLA;
- **`contracts` (Контракты):** расчет действующих обязательств по поставкам КИМ и сопровождению;
- **`commercial_proposals` (ТКП):** мониторинг статусов согласования и коэффициента конверсии КП в контракты.

## 10. Параметры сетевого шлюза и защита API (Rate Limiting & Network Resilience)

- **Rate Limiter на POST-запросы (`server.ts`):** 
  - На сервере активирован фильтр частоты запросов: лимит увеличен до **120 POST-запросов в минуту** на IP-адрес. Это гарантирует бесперебойную синхронизацию сделок CRM, автосохранение CMS и отправку форм без риска блокировок HTTP 429.
- **Отказоустойчивость клиентского слоя (`fetchWithCsrf`):**
  - При возникновении сетевого сбоя или перезапуске API-сервера клиентский компонент возвращает синтетический HTTP 503 `Response`, предотвращая появление `Uncaught (in promise) TypeError: Failed to fetch`.
  - Приложение автоматически сохраняет данные в `localStorage` и повторяет синхронизацию при восстановлении канала связи.

## 11. Эндпоинты синхронизации CMS и Базы знаний с базой данных

Для поддержки модульной архитектуры CMS в сервере реализованы выделенные эндпоинты:
- **`GET /api/db-health`:** Экспресс-проверка статуса СУБД PostgreSQL 17 и пула соединений. Возвращает `{ status: 'ok', database: 'postgresql', pool: 'active', latencyMs: N }` для строки статуса CMS.
- **`GET /api/cms/state` & `POST /api/cms/state`:** Комплексное чтение и атомарная запись полного состояния контента (пользовательские страницы, каталог ПО, каталог оборудования, направления услуг, глобальные контакты).
- **`GET /api/knowledge-base`:** Доступ к техническим статьям, стандартам ГОСТ/ISO и методикам метрологического контроля.
- **Хранилище MinIO S3 Vault:** Интеграция бакета `cad-models-3d` для трехмерных CAD-моделей (STEP, IGES, STL) с проверкой квот и доступности.

## 12. Разграничение ролей, профили доступа и персистентность пользователей

В таблице пользователей `users`, модуле персистентности `src/db/users.ts` и локальном реестре профилей реализовано строгое ролевое разделение и защита коммерческой тайны:
- **Внутренний персонал компании (`hasCrmAccess: true`):** роли `superadmin`, `admin`, `manager`, `engineer`. Доступ к воронкам сделок, формированию ТКП, общему реестру договоров, лицензий и парку приборов.
- **Внешние B2B-заказчики (`hasCrmAccess: false`):** роль `client`. При авторизации доступ предоставляется строго в автономный «Кабинет заказчика» (`ClientDashboard.tsx`) с изоляцией договоров: клиент видит только договоры и лицензии своей организации (`company`) или пустое состояние, если контракты еще не оформлены.
- **Блокировка эскалации привилегий:** панель переключения профилей скрыта от клиентов и доступна исключительно супер-администратору в режиме безопасной сессионной эмуляции.
- **Персистентность в файловом хранилище `data/users.json`:** при недоступности PostgreSQL сервер автоматически сохраняет учетные записи в `data/users.json`, гарантируя сохранность созданных пользователей между перезагрузками страницы и рестартами контейнера.
- **Мгновенные оповещения:** при регистрации сервер рассылает оповещения дежурным администраторам (Telegram, Email, аудио-алерт и лог аудита безопасности).
